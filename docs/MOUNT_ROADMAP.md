# Роадмап: duplex-монтирование дампа как диска

[К оглавлению](../README.md)

## 1. Текущее состояние

Монтирование дампа как буквы диска (Data Browser, WinFsp + winfspy) работает **только в режиме read-only**: `mount_host.py` отвечает `ACCESS_DENIED` на любую запись/удаление, дамп открыт `FileSource` в `"rb"`, политика неизменяемости образов зафиксирована в `src/modes/emmc/data_browser/sources.py`. Это осознанное проектное решение, а не временное ограничение: «удалить файл» на смонтированном диске означало бы физически перезаписать байты исходного образа.

Внедрение записи (duplex) — отдельная задача будущих версий. Этот документ фиксирует план и границы безопасности заранее, чтобы реализация не началась с обхода существующих защит.

## 2. Что даст duplex

- Создание, изменение и удаление файлов внутри разделов дампа через обычный Проводник Windows.
- Правка конфигов и данных телевизора без полного перечитывания и повторного программирования чипа.
- Подготовка модифицированного образа с последующей записью штатными операциями приложения (write User Area / per-partition).

## 3. Обязательные этапы реализации

Порядок этапов — это порядок защиты: каждый следующий этап опирается на завершённый предыдущий.

1. **Рабочая копия вместо исходника.** Duplex-монтирование разрешено только над явной рабочей копией дампа (working copy). Перед первой модификацией — свежий бэкап исходного образа (политика `sources.py`). GUI обязан показывать, над каким файлом открыта запись.
2. **Пишущий источник.** `FileSource` дополняется режимом `"r+b"` с журналированием диапазонов (offset, length, hash до/после) в sidecar-файл. RangeCache остаётся только на чтении; запись идёт через отдельный слой с проверкой границ узла (никогда за пределы `node.offset + node.size`).
3. **Операции записи в FS-бэкендах.** Для каждого файлового системы (FAT, ext) реализуются `write`/`set_file_size`/`can_delete`/`overwrite`/`created`/`set_basic_info` с честной семантикой: FAT — цепочка кластеров, ext — отдельный полный анализатор-писатель. Разделы без пишущего бэкенда остаются read-only даже в duplex-режиме (graceful-ограничение с меткой в GUI).
4. **Крэш-устойчивость.** Пишущий host обязан переживать обрыв: незавершённые транзакции откатываются по журналу диапазонов, даскопченные кластеры FAT не теряются. Обязательный тест: kill -9 host-процесса в момент записи с последующей проверкой целостности ФС и данных.
5. **GUI и подтверждения.** Отдельный режим «Mount (read-write)» с явным диалогом; подсветка того, что операции пишут в образ; запрет duplex на живом чипе (запись в чип остаётся штатным маршрутом write-операций, не файловой системой).
6. **Верификация.** Smoke-сценарии: запись-чтение-хеш, удаление, переименование, рост файла (выделение кластера), отказ на границе раздела, откат после сбоя. Аппаратная проверка — только как финальный шаг: записанный образ прошивается на тестовый чип и читается обратно.

## 4. Границы и запреты

- Никогда не писать в исходный дамп напрямую: только в рабочую копию, созданную самим приложением.
- Не смешивать duplex-монтирование со штатными write-операциями по одному образу одновременно (единая блокировка, как `_operation_lock` в orchestrator).
- Sparse- и зашифрованные (`enc`) разделы не получают пишущий путь, пока их семантика не реализована полностью (см. ограничения в OPERATIONS.md).
- RPMB/BOOT-области вне duplex-фичи.

## 5. Приоритет

Функция запланирована после стабилизации текущего read-only-браузера и не блокирует аппаратные сценарии. Оценка объёма: этапы 1–2 — небольшой рефакторинг sources/mount_host; этап 3 — основная работа (отдельно на FAT и ext); этапы 4–6 — обязательные, без них duplex не включается в GUI.
