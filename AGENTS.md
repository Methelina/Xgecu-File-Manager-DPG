# AGENTS.md — работа с Xgecu Prog

## 1. Назначение и область действия

Этот файл содержит инструкции для агентов и разработчиков, работающих с текущей версией Xgecu Prog в каталоге `emmc_continue` и его подкаталогах. Он не заменяет задачу пользователя и не распространяет автоматически разрешение на операции с оборудованием.

Рабочий язык общения и пользовательской документации — русский. Сохраняйте существующие имена API и технических полей на английском. Основная точка входа — `gui_dpg.py`, основной файл сборки — `T48_eMMC_dpg.spec`.

Документ составлен по состоянию на 30 октября 2026 года. Состояние тестов и оборудования меняется: перед выводами проверяйте актуальный код и результаты. Не превращайте исторические наблюдения в постоянные гарантии.

В родительском каталоге и соседних `new`, `new_gui`, `patch_thga_test`, `reverse`, `OR` могут находиться другие версии и исходные материалы. Не переносите туда изменения автоматически и не запускайте одноимённый родительский `gui.py` вместо этой версии.

Ранее `emmc_continue` был неотслеживаемым каталогом Git. Проверяйте текущий статус; отсутствие файла в diff не доказывает отсутствие изменений на диске. Не выполняйте массовый `git add`, очистку untracked-файлов, reset или удаление артефактов без относящейся к задаче причины и необходимого разрешения.

1. Уточните фактический результат, который нужен пользователю, по текущему запросу и принятым решениям.
2. Проверьте существующие изменения и прочитайте связанные методы/привязки.

5. Если изменилось поведение, обновите соответствующие docs. При запросе готового EXE пересоберите его.
6. Сообщите, что изменено, что реально проверено и что осталось неподтверждённым.

Не расширяйте задачу новыми режимами, зависимостями или переработкой архитектуры без необходимости. Не переписывайте рабочий код ради единообразия. Не исправляйте посторонние падения молча: отделяйте их от регрессии своей правки.

## 6. Основные функциональные инварианты

### 6.1. Области и адреса

- Userdata в GUI означает **всю аппаратную User Area**, а не только Android-раздел userdata.
- Ёмкость User Area берётся из `SEC_COUNT[212:216]`, размер каждой BOOT — из `BOOT_SIZE_MULT[226]`.
- Сектор — 512 байт, порция T48 — 16 КиБ/32 сектора.
- Диапазоны LBA включают оба конца: `(end - start + 1) × 512`.
- Запись передаёт полные порции; последний неполный блок дополняется 00 до 16 КиБ.
- Проверяйте округлённую передачу, а не только исходный размер образа.

### 6.2. Полные операции

- Полное чтение/запись: BOOT1 → BOOT2 → User Area.
- Выбранный EXT_CSD применяется после образов.
- Полная запись требует все три образа; EXT_CSD необязателен, но некорректный выбранный файл нельзя молча игнорировать.
- До образов выполняется предварительная проверка выбранного плана EXT_CSD.
- Ошибка образа/его верификации останавливает следующие этапы.
- Полное чтение не перезаписывает уже существующие Boot1.bin/Boot2.bin/userdata.img в выбранной папке.
- EXT_CSD и RPMB не входят автоматически в три файла полного чтения.

### 6.3. Стирание и пропуски

- В GUI стирание перед записью и верификация записи включены по умолчанию.
- Стирается вся выбранная область, включая остаток после меньшего образа.
- Контроль стирания: весь диапазон до 32 МиБ, иначе первые 32 МиБ.
- Пропуск RAW-заполнения 00/FF разрешён только после предварительного стирания и его контроля.
- Ожидаемое заполнение берётся из ERASED_MEM_CONT[181], а не угадывается по образу.
- Без стирания нули и FF являются данными и должны передаваться.
- Верификация RAW сравнивает весь файл, включая пропущенное заполнение.
- Остаток области за концом меньшего файла в верификацию образа не входит.

Не заменяйте ошибку контроля стирания предупреждением с последующей записью. Не выдавайте контроль первых 32 МиБ за проверку пустоты всей большой области.

### 6.4. Форматы

Полная запись аппаратных областей — RAW. Частичный Sparse-парсер используется в маршруте диапазонов таблицы. FILL не разворачивается, DONT_CARE пропускается, CRC не проверяется. Верификация выбранных RAW-сегментов не подтверждает весь развёрнутый Sparse.

Не заявляйте полноценную поддержку Sparse без реализации семантики всех нужных чанков и проверки логического результата. Исправление Sparse требует отдельного анализа границ, заполнения, ошибок формата и проверки конечных данных.

## 7. STOP, потоки и USB

Сохраняйте текущую модель владения: рабочий поток выполняет операцию и освобождает её USB-дескрипторы; GUI устанавливает запрос отмены.

- `run_task` сериализует задачи через `_operation_lock`.
- `usb_operation(stop_event)` связывает экземпляры устройства с событием рабочего потока.
- `cancel_operation` отменяет pending USB только вне `_write_active`.
- Объявленный поток записи должен получить все обещанные порции и статус завершения.
- Пакет записи ограничен 64 порциями/1 МиБ; STOP проверяется перед следующим пакетом.
- Нельзя обрывать активный поток немедленным AbortPipe или ранним выходом между его порциями.
- `begin_write` согласован с STOP общей блокировкой; флаг снимается в `finally` ожидания завершения.
- Короткая отправка USB — ошибка, а не успешная частичная запись.
- Короткий USB-блок/хвост чтения — ошибка, а не нулевые данные.
- При ошибке power-off USB всё равно должен освобождаться.

Измеренные 1.55–1.77 с STOP относятся к конкретным испытаниям; не используйте их как гарантированный максимум. Не добавляйте бесконечные повторы и не увеличивайте тайм-ауты вместо локализации ошибки.

## 8. Перезапуск перед верификацией

Текущий специальный recovery относится только к OSError 121 при **чтении ответа на отправленную команду power-off**. После него закрываются/открываются USB-дескрипторы, выполняются init, чтение регистров и сравнение CID. Затем всё равно нужен полный предусмотренный readback.

Не расширяйте этот catch на всю верификацию, запись команд или произвольные USB-ошибки. Ошибка отправки, другой код, невозможность открыть T48, init failure, смена CID или несовпадение данных должны оставаться ошибками.

В финальном `close` предупреждение power-off скрыто по принятому решению, но освобождение USB обязательно. Не возвращайте повторяющееся предупреждение без причины, относящейся к задаче. При этом не утверждайте, что отсутствие сообщения доказывает физическое снятие питания.

## 9. Автоподбор и частоты

- Пресет «Авто» — начальный выбор GUI.
- Эталон получается на 8 МГц с проверкой регистров и данных.
- Кандидаты проверяются по CID/CSD, геометрии и повторному чтению начала/середины/конца User Area.
- Автоподбор не стирает и не записывает пользовательские области.
- Успешный init без чтения не достаточен для принятия кандидата.
- Кеш процесса учитывает VCCQ/шину и используется следующими сессиями.
- «Инит eMMC» явно сбрасывает кеш и запускает новый подбор.
- Кеш не привязан к CID; после замены чипа требуется новый init.
- Настройки существующей сессии не меняются при переключении GUI для следующей операции.

Рабочие частоты: 8, 16, 20, 30 МГц. Для 30 код требует VCCQ 1.8 V. THGA Legacy 30 (`HS_TIMING=0`) остаётся экспериментальным разгоном выше паспортного предела Legacy 26 МГц. High-Speed 30 и Legacy 30 — разные варианты.

**40 МГц исключены по решению пользователя. Не возвращайте их в приложение в рамках обычного исправления.** Успех архивного опыта на другом CID не даёт основания включать режим для текущего чипа.

Частота, физическая ширина шины и напряжения не измерены прибором. Не называйте их инструментально подтверждёнными по одному значению selector или EXT_CSD.

## 10. EXT_CSD и необратимые настройки

Разрешённые пользовательские записи: 177, 178, 179, 162. Поле 160 только читается. Не добавляйте произвольную запись остальных байтов под видом восстановления 512-байтного файла.

- Форматы файла: ровно 512 или 544 байта.
- Файл не подменяет свежий снимок подключённого чипа.
- Перед записью проверяются CID, исходное значение и соответствие настроек подключения.
- PARTITION_ACCESS в поле 179 сохраняется.
- План из файла: 177 → 179 → 162 → 178, защита последней.
- RST_N_FUNCTION и постоянная защита требуют соответствующего подтверждения.
- `allow_otp=True` предполагает уже полученное подтверждение вызывающей стороной.
- Readback RST_N_FUNCTION не доказывает физическую работу RST_n.

Принятое поведение: несовпадение readback отдельного разрешённого поля логируется, фактический снимок сохраняется, план продолжается. Не превращайте его незаметно в успех и не меняйте правило продолжения без запроса. Транспортные ошибки и смена CID не должны маскироваться этим правилом.

Общий итог полной записи может следовать за предупреждениями EXT_CSD. В отчётах указывайте несовпавшие поля отдельно, не называйте весь набор настроек подтверждённым.

## 11. Работа с реальным оборудованием

Разделяйте действия:

| Действие | Требование |
|---|---|
| Чтение кода/логов, mocks, сборка, запуск GUI без операции | Обычная работа по задаче |
| Init/read-only probe | Проверить занятость T48, параметры и влияние volatile-настроек |
| Запись/стирание eMMC | Нужно применимое разрешение на конкретный чип/область; проверьте контекст и сохранность данных |
| OTP/постоянная защита | Подтверждение конкретных изменений; сохранять диалоги защиты |
| Перепрошивка T48 | Отдельное изменение самого программатора; прежнее разрешение писать eMMC его не покрывает |

Ранее пользователь разрешал тестовые записи на установленный пустой чип и проверки 8/30 МГц. Не считайте это доказательством, что любой будущий чип всё ещё пустой, и не требуйте повторного согласования для уже явно разрешённого неизменившегося сценария.

Перепрошивка T48 отклонена. Offline-кандидаты в firmware_candidates не устанавливать, bootloader-переходы не запускать без нового явного изменения этого решения пользователем.

Не запускайте аппаратную проверку одновременно с активной GUI-операцией. Сначала выполняйте доступную проверку чтением. В аппаратном отчёте фиксируйте CID, область, LBA, длину, режим, хеши и реальный результат. Не считайте счётчик отправленных байтов доказательством программирования.

## 12. GUI и визуальные требования

- GUI-состояние меняется через поток DPG/frame callback, без прямых обновлений виджетов из USB-потока.
- Журнал, числовой прогресс и фаза передаются отдельными callback.
- При смене темы сохраняйте контраст активных/неактивных состояний.
- «Инит eMMC»: светлая тема `#AFFC41`, тёмная `#548C2F`, текст тёмной темы белый.
- Все SpinnerOption имеют разделительные линии.
- Кнопка «Scatter -> GPT» удалена; наличие старого метода не является поводом вернуть её.
- Название окна — Xgecu Prog.
- Выбран строгий логотип: logo_technical.svg; иконки xgecu_prog.png и xgecu_prog.ico.
- NAND/SPI показываются как режимы в разработке, не как работающие функции.
- Поиск/фильтр журнала не должен уничтожать исходные строки; копирование включает полный журнал.

В тестах реактивного GUI при необходимости используйте `Clock.tick()` и `Builder.sync()`. Не полагайтесь только на обычный `walk()` для виджетов неактивных Screen. Не фиксируйте устаревший цвет вместо актуальной семантики темы.

- Комментарии в коде: только заголовки блоков и короткие однострочные пояснения неочевидного поведения. Многострочные рассказы, история изменений и ссылки на другие проекты в комментариях не пишутся.

```text
    Patchnote vX.Y.Z-1 (<автор той версии>):
      ...
#>
```

- Для Python-точек входа тот же блок — в module docstring.
- Патчноты пишутся от новых к старым; автор указывается в скобках в каждой строке Patchnote; никаких многострочных процессуальных отчётов внутри патчнотов.
- Не редактируйте патчноты чужих версий — только добавляйте новые записи сверху со своим именем.

## 19. Политика использования субагентов

Всегда предпочитайте использование субагентов для любых подзадач, которые можно изолировать и которые не требуют глобального контекста. Используйте субагентов для:

- Генерации кода в конкретных модулях
- Тестирования и валидации
- Исследований или сбора информации
- Разведки (поиск файлов, поиск кода, сопоставление паттернов)
- Параллелизуемых задач

### 19.1. Языковая политика

Все вызовы субагентов, промпты к субагентам и внутреннее рассуждение должны быть на **английском**. Русский используется только в итоговом пользовательском отчёте/резюме. Это сохраняет промпты субагентов однозначными, избегает накладных расходов на перевод и гарантирует, что grep-able ссылки (пути к файлам, идентификаторы, паттерны) возвращаются на каноническом языке проекта.

### 19.2. Типы субагентов

Доступны два типа субагентов — используйте правильный и предоставляйте правильный контекст:

- **`explore`** — быстрый субагент для поиска файлов, поиска кода, сопоставления паттернов, разведки и сбора информации. Требует **абсолютные пути** для любых корней поиска или целевых директорий. Возвращает только точные ссылки (пути к файлам с номерами строк или точные фрагменты кода), чтобы основной агент мог продолжить с целевым `grep` или `read` без повторной проверки нерелевантных данных. Используйте для всех задач разведки.

- **`general`** — мощный агент кодирования/валидации, требующий детального входного контекста с абсолютными ссылками и чёткими, гранулярными инструкциями. Он склонен к пустому рассуждению и самоуправляемому поведению при размытых промптах или недостаточных ограничениях. Используйте только когда у вас есть хорошо обозначенная, пошаговая задача с явными путями к файлам, целевыми функциями и ожидаемыми результатами. Всегда включайте конкретный контекст — не оставляйте место агенту для изобретения собственных подцелей.

**Команды оболочки:** субагенты должны использовать **только команды Windows**. Они имеют тенденцию по умолчанию использовать Unix-команды (`ls`, `la` и т.д.) при скудном контексте, что вызывает ошибки на `win32`. Всегда указывайте PowerShell-эквиваленты (`Get-ChildItem`, `Select-String`, `Test-Path` и т.д.) в промптах. Субагенты **никогда** не должны запускать python/pytest/git или трогать файлы за пределами явно перечисленных абсолютных путей.

**Git destructive-restore ban для субагентов (ОБЯЗАТЕЛЬНО, повторять дословно в каждом промпте кодирующего субагента):** "Git is READ-ONLY: `git status`, `git log`, `git diff`, `git show` для инспекции только. Вы НЕ ДОЛЖНЫ запускать `git checkout`, `git restore`, `git reset`, `git stash`, `git clean`, `git apply` или любую команду, изменяющую рабочее дерево, индекс или историю. Вы НЕ ДОЛЖНЫ 'ремонтировать', 'очищать' или 'восстанавливать' рабочее дерево до HEAD, stash или любого ref — если рабочее дерево выглядит несовместимым с вашими ожиданиями, ОСТАНОВИТЕСЬ и сообщите о расхождении в DEVIATIONS вместо исправления. Незакоммиченные изменения рабочего дерева драгоценны и принадлежат оркестратору/пользователю; перезапись их состоянием HEAD — это потеря данных." Короткая фраза "Git READ-ONLY" одна **НЕ ДОСТАТОЧНА** — субагенты интерпретировали её как "нет коммитов" и откатили незакоммиченную работу.

**Атомарность:** задачи субагентов должны быть атомарными — никакой многозадачности или многостадийной работы в одном вызове. Многошаговые или многофайловые задания заставляют агента спорить в переполнении контекста и самоуправляемых ошибках. Предпочитайте вызов нескольких субагентов параллельно, каждый с одной изолированной задачей и (идеально) одним файлом, вместо передачи одному агенту широкого пакета. **Не порождайте более 4 субагентов в одном батче** — превышение этого лимита вызывает контекстный трэшинг и ошибки. **1 файл = 1 субагент**; давайте точные абсолютные пути к файлам, никогда родительские директории (иначе они сканируют миллионы файлов).

**Детализация промпта:** при отправке `general` (кодирующего) субагента включайте правила документирования кода (формат synopsis + patch notes, стиль заголовков секций в коде) в промпт, чтобы агент их применял. Короткие, абстрактные промпты для субагентов ведут к застреванию в пустых циклах рассуждений и хаосу — всегда предоставляйте конкретный контекст: явные пути к файлам, целевые функции, ожидаемые результаты и любые релевантные ограничения из стандарта документирования кода. Только оркестратор пишет тесты.

**Формат отчёта:** каждый субагент отчитывается в точном формате `START` / `END` / `DEVIATIONS`.

**Время выполнения:** субагенты должны фиксировать время начала в начале выполнения задачи и сообщать время завершения в финальном выводе. Это позволяет основной модели калибровать будущие задачи, выявляя те, что занимают непропорционально много времени.

### 19.6. Контракт explorer-субагента

При отправке субагента для разведки (поиск файлов, поиск по кодовой базе, сопоставление паттернов и т.д.) инструктируйте его возвращать только результаты, напрямую релевантные заявленной задаче:

- **Возвращайте только точные ссылки** — пути к файлам с номерами строк (например `src/main.py:165`) или точные фрагменты кода, а не полные дампы файлов.
- **Фильтруйте агрессивно** — отбрасывайте почти-попадания и касательные совпадения перед отчётом.
- **Сохраняйте grep-способность** — цитируйте точные строки, идентификаторы и regex-паттерны дословно, чтобы основной агент мог сразу `grep` по ним без перечитывания.
- **Ограничивайте размер результатов** — никогда не возвращайте больше, чем нужно для следующего детерминированного решения; нацеливайтесь на одно конкретное обнаружение на запрос разведки.
- **Синтезируйте, не копите** — исследователь должен резюмировать свой вывод в 1–2 предложения и привести доказательства, а не сваливать сырой вывод инструментов.

Это держит контекст основного агента компактным: он может продолжить с точным `grep` или целевым `read` по указанному пути/строке вместо перебора килобайт нерелевантных данных.

**Отчёты разведки:** агенты должны записывать свои находки в файл `tmp\recon\<task-name>.recon.md` (проект-локально, по политике временных файлов) для повторного использования в будущих сессиях. Каждый отчёт включает описание задачи и результаты/выводы. Это избегает повторного открытия той же информации в последующих запусках.

## 20. Стандарт документирования кода

Каждый файл кода должен содержать блок комментария-синопсиса в начале с patch notes, в стиле проекта (Python-модули используют module docstring; PowerShell использует блок комментария):

```
"""
<Short description of the module and its role in the architecture.>

src/<module>.py
Version:     X.Y.Z
Author:      <Author Name>
Updated:     YYYY-MM-DD

Patch Notes vX.Y.Z (<Author>):
  [+] <what was added/fixed, one [+] line per logical change>.
"""
```

Правила:

- **Если у файла нет синопсиса:** отправьте субагента для поверхностного анализа git-истории этого файла (`git log --follow -p -1 <file>` и недавние сообщения коммитов) и добавьте синопсис с приблизительными patch notes в начало. Держите лаконично — один блок, краткое описание, строки метаданных (путь, версия, автор, обновлено) и секцию `Patch Notes`.
- **Автор всегда указывается точно так, как согласовано в начале сессии** — никаких других имён, никаких заметок о процессе реализации в файлах проекта.
- **Дисциплина patch notes:** каждое изменение добавляет новый блок `Patch Notes vX.Y.Z` (или расширяет текущий), поднимает версию, устанавливает `Updated:`.

**Заголовки секций в коде:** разделяйте логические блоки, используя стиль комментариев автора:

```python
# ---------------------------------------------------------------------------
# RAG retrieval pipeline (semantic search via Qdrant + DuckDB fallback).
# <one-paragraph explanation of the data flow and key constants>
# ---------------------------------------------------------------------------
```

## 21. Конвенции документации

**Таблица статуса после каждого полного прогона сьюта (ОБЯЗАТЕЛЬНО).** После каждого полного офлайн-прогона сьюта оркестратор отчитывается план todo в виде таблицы с четырьмя состояниями и фиксированными маркерами: ✅ done; ➡️ queued (с указанием за каким завершённым шагом следует); 🚧 in progress; ❌ impossible (с причиной). Таблица — каноническое видимое состояние плана — держите её в синхронизации с инструментом todowrite.

**Нет жестких переносов строк (hard wrap) в документах.** При написании и правке документов НЕ делать механических переносов строк по фиксированной ширине: один абзац = один непрерывный блок текста без разрывов внутри; перевод строки разделяет только настоящие абзацы, пункты списков, строки таблиц и заголовки. Экраны у всех разные — hard-wrapped текст на большом мониторе выглядит как вертикальная «строка для телефона» и рассыпается при любой правке; приложение для чтения само делает переносы как надо.

## 22. ПОЛИТИКА РЕДАКТИРОВАНИЯ ФАЙЛОВ (ОБЯЗАТЕЛЬНО): только встроенные инструменты, шелл НИКОГДА не редактирует

**Запрет на шелл-редактирование файлов.** Файлы создаются, читаются и правятся ТОЛЬКО встроенными инструментами (`read` / `edit` / `write`). Шелл (pwsh, cmd, python-однострочники, `Set-Content`, `Get-Content | ...`, `>` redirect, `-replace`-пайпы и т.п.) НЕ используется для редактирования, перекодирования, конвертации или «быстрых правок» файлов — ни для исходников, ни для документов, ни для конфигов.

Причины (два задокументированных инцидента 2026-11-12):
- `Get-Content | Set-Content` склеил README.md в одну строку и перекодировал UTF-8 (эмодзи → `??`), файл пришлось восстанавливать из HEAD;
- python-однострочник с заменами сломался на экранировании кавычек и не выполнился — редактирование через шелл ненадёжно в принципе.

Шелл разрешён ТОЛЬКО для: запуска тестов (`pytest`, `compileall`), git (read-only + commit/push по команде), запуска приложений/фоновых процессов, чтения БД через python в **проектный** temp-файл (UTF-8, `PYTHONIOENCODING=utf-8`) с последующим `read` этого файла встроенным инструментом, и Diagnostics через grep/select-string. Любое изменение содержимого файла — только `edit`/`write`.

**Ограничение переноса строк в документах** (бывший reflow-рецепт удалён — он был шелл-редактированием): hard-wrap в markdown исправляется только точечными `edit`-заменами; абзац = один непрерывный блок текста без механических переносов.

## 23. ПОЛИТИКА ВИЗУАЛЬНОЙ ВАЛИДАЦИИ (ОБЯЗАТЕЛЬНО)

Визуальная валидация — любая проверка, требующая взгляда на рендеренный вывод (скриншоты, Game View, Scene View, освещение, тени, цвета, glow/SSS, пост-обработка) — может выполняться ТОЛЬКО ПОЛЬЗОВАТЕЛЕМ в основной сессии. Ни Оркестратор, ни никакой субагент не могут делать скриншоты и пытаться их интерпретировать, и агенты НЕ ДОЛЖНЫ зацикливаться, пытаясь сделать/прочитать скриншоты для «верификации» визуальных результатов.

Правила:

- Когда задача достигает точки, требующей визуальной валидации, субагент ДОЛЖЕН ОСТАНОВИТЬСЯ и закрыть/завершить свою сессию, затем передать пользователю для валидации в основной сессии.
- Агент может ПОДГОТОВИТЬ сцену для визуальной проверки (разместить объекты, свет, настроить переключатели), но НЕ ДОЛЖЕН делать скриншот/скриншоты или анализировать отрендеренные изображения.
- Если визуальный результат должен быть подтверждён, сообщите точно, что было подготовлено/изменено, и остановитесь — пользователь валидирует визуально и сообщает обратно.

## 24. Политика безопасности Git (ОБЯЗАТЕЛЬНО)

Git может использоваться **только для read-only инспекции** — изучение истории, просмотр диффов, понимание контекста кода, чтение сообщений коммитов. Никакая git-операция, модифицирующая рабочее дерево, состояние ветки или историю коммитов, не разрешена, если пользователь не запросил её явно и явно (commit/push происходят ТОЛЬКО по явной команде пользователя).

**Запрещённые операции (если пользователь не командует конкретной явно):**

- `git checkout`, `git restore`, `git reset` (любой режим), `git clean` — уничтожают незакоммиченную работу
- `git merge`, `git rebase`, `git cherry-pick`, `git revert` — меняют историю ветки или применяют чужые коммиты
- `git stash`, манипуляции с `git reflog` — риск потерять отслеживание незакоммиченных изменений
- `git apply`, `git checkout -- <file>` — могут молча перезаписать незакоммиченные правки
- `git rm` — ставит в stage удаления, которые могут быть непреднамеренными
- `git push`, `git fetch` с merge — могут внести неожиданное удалённое состояние

**Разрешённые read-only операции:**

- `git status`, `git log`, `git diff` — просмотр текущего состояния и истории
- `git show`, `git blame` — инспекция конкретных коммитов и авторства строк
- `git ls-files`, `git rev-parse` — список отслеживаемых файлов и разрешение refs
- Копирование нужных коммитов или ревизий **локально во временную отдельную папку** только для изучения (например `git archive` или `git show` + extract). Это разрешено **только для инспекции** и не должно использоваться для восстановления перезаписанных файлов, перезаписи рабочего дерева или модификации текущей ветки. Не храните эти копии дольше немедленной потребности в изучении; очистите временную папку после (под `tmp\`, по политике временных файлов).

Эти ограничения существуют, потому что git write/restore операции неоднократно вызывали полную потерю незакоммиченной работы. В сомнительных случаях используйте инструменты `read`/`write`/`edit` напрямую на файлах вместо git для восстановления или модификации контента.

**Приватные файлы никогда не коммитятся несанеризированными:** конфиги с API ключами, сгенерированные проекции, данные БД, логи, tmp, кэши. Отслеживаемый санитизированный прототип — это `.example` файл (схема = тип настроек в коде; держите его свободным от личных идентификаторов и абсолютных путей).

## 25. Политика фоллбэков и обработки ошибок (ОБЯЗАТЕЛЬНО)

Тихая деградация запрещена. Фоллбэк, невидимый в логах, превращает локальную деградацию в бесконечную перекрёстную отладку по всей кодовой базе.

Правила:

1. **Каждый фоллбэк должен логироваться как tagged warning** (`logger.warning`, стабильный модульный тег, сообщение содержит слово `fallback:` и называет, что деградировало). Поэлементный шум на горячем пути может использовать `logger.debug`, но всё, что деградирует целую сессию, соединение или результат, должно быть `logger.warning`. Пример: `logger.warning("[LLM] fallback: Ollama endpoint unreachable, switching to LLaMA backend")`.
2. **Нет тихих `except Exception: pass/continue`.** Каждый `except` блок должен либо логировать (см. правило 1), либо ре-рейзить. Голый `except:` запрещён; всегда захватывайте `as exc` при логировании.
3. **Предпочитайте проактивный try/except в точках сомнения.** На любой границе I/O, парсинге протокола, опциональном колбэке или сайте внешнего взаимодействия оберните сомнительную операцию в try/except с залогированным фоллбэком ВМЕСТО того, чтобы пускать скрипт крашнуться и заставлять позже охотиться на неудачу по всей кодовой базе. Fail soft, log loud.
4. **Фоллбэки должны быть обнаруживаемы.** Используйте стабильный префикс сообщения (`"<module> fallback: ..."`), чтобы `grep -r "fallback:"` перечислял каждую точку деградации в проекте.
5. Новые код-ревью (верификация оркестратором) должны проверять эту политику наряду с тестами.
